Binary Search Patterns

Rotated Array
Cheat Sheet

Two essential problems — finding the minimum and searching for a target — both solved in O(log n) using binary search on a rotated sorted array.

Problem Setup
Original
[1, 2, 3, 4, 5, 6] — sorted ascending
After rotation (k=2)
[3, 4, 5, 6, 1, 2] — pivot between 6→1
Elements wrap from the end to the beginning
Key property
At least one half is always fully sorted
This is what makes O(log n) possible
Two Problems
Problem 1 — Find Minimum
Find the minimum element (the rotation pivot). Always returns a value.
Loop condition: left < right (strict)
Problem 2 — Search Target
Find a specific target. Returns index or -1 if not found.
Loop condition: left <= right (inclusive)
O(log n) time O(1) space
The Core Insight
💡
One half is always sorted When you split a rotated array at mid, either the left half [left..mid] or the right half [mid..right] is guaranteed to be fully sorted.
⚠️
Test the sorted half first Check if your target lies within the sorted half. If yes, narrow to it. Otherwise, go to the other half.
Left Sorted Check
Condition
nums[left] <= nums[mid]
If left ≤ mid value, the segment [left..mid] is sorted (no rotation in this half).
Mid Calculation
❌ Avoid overflow
(left + right) / 2
Can overflow with large indices
✅ Safe formula
left + (right - left) / 2
Integer division, no overflow

Find Minimum — Logic
If nums[mid] > nums[right]
Min is in the right half → left = mid + 1
Mid is above the rotation. The drop happens to the right.
Else (nums[mid] <= nums[right])
Min could be mid or further left → right = mid
Note: right = mid (not mid-1) — mid itself could be the min.
Loop ends when
left == right → nums[left] is the minimum
Why compare with nums[right]?
🎯
Relative position to pivot Comparing mid to right tells us which half has the rotation point. The minimum element is always just after the "drop" — where a larger value is followed by a smaller one.
⚠️
Never compare with nums[left] Since we search rightward for the minimum, anchoring to the right boundary is stable. Comparing with left doesn't give reliable direction.
Code
class Solution {
  public int findMin(int[] nums) {
    int left  = 0;
    int right = nums.length - 1;

    // left < right  (strict — no equal)
    while (left < right) {
      int mid = (right + left) / 2;

      // mid is in the "high" part
      if (nums[mid] > nums[right]) {
        // min must be to the right
        left = mid + 1;
      } else {
        // mid could be the min
        right = mid; // not mid-1!
      }
    }
    // left == right == index of minimum
    return nums[left];
  }
}

Search Target — Logic
Step 1 — Found?
nums[mid] == target → return mid
Step 2 — Left sorted? nums[left] <= nums[mid]
If nums[left] <= target < nums[mid]
→ Target is in left half: right = mid - 1
Otherwise
→ Search right: left = mid + 1
Step 3 — Right sorted (else branch)
If nums[mid] < target <= nums[right]
→ Target is in right half: left = mid + 1
Otherwise
→ Search left: right = mid - 1
Not found
Loop ends with left > right → return -1
Code
class Solution {
  public int search(int[] nums, int target) {
    int left  = 0;
    int right = nums.length - 1;

    // left <= right  (inclusive)
    while (left <= right) {
      int mid = left + (right - left) / 2;

      if (nums[mid] == target) return mid;

      // Left half is sorted
      if (nums[left] <= nums[mid]) {
        if (nums[left] <= target
            && nums[mid] > target) {
          right = mid - 1; // target in left
        } else {
          left  = mid + 1; // search right
        }
      } else { // Right half is sorted
        if (nums[right] >= target
            && nums[mid] < target) {
          left  = mid + 1; // target in right
        } else {
          right = mid - 1; // search left
        }
      }
    }
    return -1; // not found
  }
}

Common Pitfalls
❌ Using right = mid - 1 in findMin
The minimum could be at mid itself — you'd skip it.
❌ Using left <= right in findMin
The loop never terminates when left == right with inclusive condition.
❌ Comparing mid with left in findMin
Anchoring to right boundary is the correct approach for locating the drop.
❌ Missing = in left sorted check
nums[left] <= nums[mid] — the <= handles the single-element case.
Edge Cases
Not rotated: [1,2,3,4,5]
findMin: always takes else branch → works fine
search: degrades to standard binary search
Single element: [7]
findMin: loop never runs, returns nums[0]
search: checks single element once
Two elements: [2,1]
findMin: mid=0, nums[0]>nums[1] → left=1, returns nums[1]=1
Target not in array
search: left > right ends the loop → returns -1
