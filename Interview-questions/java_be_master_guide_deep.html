Q1What is JVM? Difference between JVM, JRE, and JDK?▾
🍳 Real World Analogy

Think of writing a recipe (Java source code). The JDK is your full kitchen — oven, knives, pans, the recipe book — everything to cook AND eat. The JRE is just the dining table and microwave — enough to heat food (run programs) but you can't cook fresh food (compile code). The JVM is just the microwave itself — it only executes already-prepared (compiled) bytecode.

When you write a Java program, it goes through this process:

// The Java execution pipeline

Java Source Code (.java)
        ↓  javac (compiler in JDK)
Bytecode (.class files)
        ↓  JVM
Machine Code (specific to OS/CPU)
        ↓
Program Runs

JVM (Java Virtual Machine) is the engine that reads bytecode and converts it to machine-level instructions your CPU understands. It is platform-specific — there is a different JVM for Windows, Linux, and macOS. But the bytecode is the same everywhere. This is the "Write Once, Run Anywhere" guarantee.

JRE (Java Runtime Environment) contains the JVM plus all the standard libraries (java.lang, java.util, java.io etc.). If a user just wants to RUN a Java application, JRE is enough. They don't need compilers.

JDK (Java Development Kit) is the full package for developers. It contains JRE + compiler (javac) + debugger (jdb) + jar tool + javadoc + many more tools. If you're writing code, you need JDK.

"JDK is used for development — it contains the compiler and debugger. JRE is just for running Java programs — it has the JVM and standard libraries. JVM is the runtime engine that actually executes the bytecode and makes Java platform independent."

Q2Explain JVM Architecture — Class Loader, Runtime Data Areas, Execution Engine▾

The JVM has three major subsystems that work together to run your program:

// JVM Architecture Overview

Your .class files
      ↓
┌──────────────────────────────────────┐
│         CLASS LOADER SUBSYSTEM       │
│  Bootstrap → Extension → Application │
└──────────────────────────────────────┘
      ↓
┌──────────────────────────────────────┐
│         RUNTIME DATA AREAS           │
│  Heap | Stack | Metaspace | PC | NMS │
└──────────────────────────────────────┘
      ↓
┌──────────────────────────────────────┐
│         EXECUTION ENGINE             │
│  Interpreter | JIT Compiler | GC     │
└──────────────────────────────────────┘

1. Class Loader Subsystem

Loads your .class files from disk into JVM memory. This happens in 3 phases:

1
Loading

Reads the .class file binary data. Checks if the class is already loaded (to avoid duplicates).

2
Linking

Verifies bytecode is valid and not tampered (Verification). Allocates memory for static variables and sets default values (Preparation). Replaces symbolic references with actual memory references (Resolution).

3
Initialization

Runs static initializer blocks and assigns values to static variables. This is when static { ... } blocks execute.

There are 3 built-in class loaders and they follow the Parent Delegation Model — when a class needs to be loaded, it always asks the parent loader first before trying itself. Bootstrap ClassLoader loads core Java classes (java.lang.*). Extension ClassLoader loads from ext directory. Application ClassLoader loads your application classes.

2. Runtime Data Areas

Heap

All objects and arrays. Shared by all threads. Where GC runs.

Stack

Per-thread. Method call frames. Local variables. Auto-cleaned when method ends.

Metaspace

Class definitions, method names. Native memory. Grows dynamically.

Code Cache

JIT-compiled native code stored here for reuse.

PC Register

Per-thread pointer to currently executing instruction.

3. Execution Engine

The part that actually runs your code. It has three components:

  • Interpreter — reads and executes bytecode one instruction at a time. Simple but slow — same bytecode is re-interpreted every time it runs.
  • JIT Compiler (Just-In-Time) — detects "hot" code (methods called many times) and compiles them to native machine code. Stores in Code Cache. Next time that code runs, it uses the fast native version instead of interpreting. This is why Java gets faster the longer it runs.
  • Garbage Collector — automatically frees heap memory occupied by objects that are no longer reachable.
Q3Thread-specific runtime data areas — what are they and what do they store?▾

When you create a new thread in Java, the JVM allocates three private memory regions just for that thread. Nobody else can see or touch them.

Thread-Private Areas

JVM Stack — This is the most important one to understand. Every time a method is called, a new "stack frame" is pushed onto this stack. The frame contains: local variables (int x=5, String name etc.), operand stack (for intermediate calculations), and a reference to the constant pool. When the method returns, its frame is popped. If you call too many methods without returning (deep recursion), the stack grows until it hits its limit and you get StackOverflowError.

// Stack grows with each method call
void main() {
    methodA();                   // Frame 1 pushed
}
void methodA() {
    int x = 5;                   // x lives in methodA's frame
    methodB();                   // Frame 2 pushed
}                                // Frame 2 popped when methodA returns
void methodB() {
    // Frame 3 on stack
}                                // Frame 3 popped

PC Register (Program Counter) — A tiny pointer that says "this thread is currently executing instruction number X." Each thread needs its own because threads run independently and can be at completely different points in execution at the same time.

Native Method Stack — Same concept as JVM Stack but for native (C/C++) methods called through JNI (Java Native Interface).

Shared Areas (Across All Threads)

Heap and Metaspace are shared. This is why you need synchronization when multiple threads access the same object — they're both reading/writing the same heap memory.

📋 Key Insight for Interviews

Local variables on the stack are automatically thread-safe because each thread has its own stack. Instance variables on the heap are NOT thread-safe because all threads share the heap. This is the root cause of most concurrency bugs.

Memory impact of thread creation: Each new thread allocates a fresh JVM Stack — default size is 512KB to 1MB depending on JVM settings. If you create 1000 threads, that's up to 1GB just for stacks! This is why thread pools (ExecutorService) and virtual threads (Java 21) are preferred over creating raw threads.

Q4Java Memory Model (JMM) and Happens-Before relationships — explain in detail▾
🍳 Analogy

Imagine two people (threads) editing a shared Google Doc (main memory) but each person has their own offline notepad (CPU cache). Person A writes "meeting at 3pm" on their notepad. Until they hit sync, Person B's notepad still shows the old value. The JMM defines the rules: when must a person sync their notepad to the shared doc so others can see the update?

Modern CPUs don't read/write directly to RAM every time — they use caches (L1, L2, L3) for performance. This means a value written by Thread A might sit in A's CPU cache and Thread B reading the same variable from its own cache sees the old value. This is the visibility problem.

The Java Memory Model is a specification that defines exactly when writes made by one thread are guaranteed to be visible to another thread. Without these guarantees, you could write correct-looking code that fails randomly depending on CPU behavior.

Happens-Before (HB) — The Core Concept

If action A happens-before action B, then all effects of A (memory writes) are guaranteed visible to B. The JMM defines these specific HB rules:

Program Order Rule

Each statement in a single thread HB the next statement in that same thread. Within one thread, code always appears to execute in order.

Monitor Lock Rule

Releasing a synchronized lock (monitorexit) HB any subsequent acquisition of that same lock (monitorenter). So when Thread A leaves a synchronized block, all its writes become visible to Thread B when B enters the same synchronized block.

Volatile Variable Rule

A write to a volatile variable HB every subsequent read of that variable. This is the cheapest way to ensure visibility without full synchronization.

Thread Start Rule

Thread.start() HB any action in the started thread. Everything done before starting a thread is visible to that thread when it begins.

Thread Join Rule

All actions in a thread HB the return of join() on that thread. After join() returns, you can safely read values written by the joined thread.

// Without HB guarantee — this is BROKEN
boolean ready = false;
String message = null;

// Thread A
message = "hello";   // write to message
ready = true;        // write to ready

// Thread B (may see ready=true but message=null!)
if (ready) {
    System.out.println(message); // could print null!
}

// Fix with volatile — establishes HB
volatile boolean ready = false;
// Now volatile write to ready HB volatile read of ready
// Thread B is guaranteed to see message="hello" when ready=true
Q5volatile keyword — what does it solve? What does it NOT solve?▾

volatile is a keyword you put on a variable to make two guarantees:

Guarantee 1 — Visibility: Every read of a volatile variable goes directly to main memory. Every write to a volatile variable flushes directly to main memory. No CPU caching. This means if Thread A writes to a volatile variable, Thread B will always see the latest value.

Guarantee 2 — No reordering: The JVM/CPU will not reorder instructions around a volatile read/write. This prevents subtle ordering bugs.

// GOOD use of volatile — simple flag
class Worker implements Runnable {
    private volatile boolean running = true;
    
    public void run() {
        while (running) {        // always reads fresh value from memory
            doWork();
        }
    }
    
    public void stop() {
        running = false;          // immediately visible to the running thread
    }
}
⚠️ What volatile does NOT solve

volatile does NOT guarantee atomicity. The operation count++ looks like one step but is actually three: READ the value → INCREMENT it → WRITE it back. If two threads do this simultaneously, both might read the same value and both write the same incremented value, losing one increment. For this, use AtomicInteger or synchronized.

// BROKEN — volatile doesn't fix this
volatile int count = 0;
count++; // NOT atomic — still a race condition!

// FIXED with AtomicInteger
AtomicInteger count = new AtomicInteger(0);
count.incrementAndGet(); // atomic — uses CAS (Compare-And-Swap)

// FIXED with synchronized
synchronized void increment() {
    count++; // only one thread at a time
}
🎤 Perfect interview answer

"volatile solves the visibility problem — it ensures every thread sees the latest value from main memory without CPU caching. But it does not solve atomicity — for compound operations like count++, you need AtomicInteger or synchronized."

Q6Production service has Full GC spikes causing response time delays — how do you analyse and fix?▾

This is a very common 10-12 LPA production scenario question. The interviewer wants to see if you understand GC, profiling tools, and can think like a senior engineer.

What is Full GC? Full GC (or Major GC) is when the JVM pauses ALL application threads — called "Stop-The-World" — to clean up the entire heap including the Old Generation. During this pause, no requests are processed, causing response time spikes. A healthy app should rarely have Full GCs.

Step-by-Step Investigation

1
Enable GC Logging

Add to JVM startup: -Xlog:gc*:file=/logs/gc.log:time,uptime. This captures every GC event with timestamps and duration.

2
Analyse with GCEasy or GCViewer

Upload the gc.log to GCEasy.io. It shows GC frequency, pause times, heap utilization over time, and tells you what's wrong.

3
Check Heap Usage Pattern

If heap usage keeps growing and never fully drops after GC → memory leak. If heap is always near max → increase Xmx or fix excessive object creation.

4
Java Flight Recorder (JFR)

Add -XX:+FlightRecorder. JFR continuously records profiling data with very low overhead. Analyze with JDK Mission Control to find which classes are consuming most heap.

5
Heap Dump Analysis

Add -XX:+HeapDumpOnOutOfMemoryError. When OOM occurs, a heap dump is saved. Open with Eclipse MAT (Memory Analyzer Tool) to find the objects holding most memory.

Q7MetaSpace vs PermGen — what changed in Java 8 and why?▾

Before Java 8, the JVM had a special heap region called PermGen (Permanent Generation) that stored class metadata — class names, method definitions, the bytecode itself, constant pools. It was part of the Java heap, fixed in size (default ~64MB), and you had to guess the right size upfront.

The problem: modern applications (especially with frameworks like Spring, or apps that use dynamic class generation) load thousands of classes. If PermGen ran out, you got the dreaded OutOfMemoryError: PermGen space. The fix was to keep tuning -XX:MaxPermSize blindly.

Java 8 removed PermGen entirely and replaced it with Metaspace, which lives in native memory (the OS memory outside the Java heap). By default, Metaspace grows automatically as needed — no more hard limit. You can cap it with -XX:MaxMetaspaceSize if you want to prevent unbounded growth.

FeaturePermGen (Java 7 and below)Metaspace (Java 8+)
LocationInside Java HeapNative OS Memory
Default sizeFixed ~64MBUnlimited (auto-grows)
OOM riskVery high with many classesMuch lower
GC impactCollected with Full GCCollected on class unload
Tuning flag-XX:MaxPermSize-XX:MaxMetaspaceSize
💡 Metaspace can still cause OOM

If your app dynamically generates classes (e.g. heavy use of proxies, Groovy scripts, JSP hot-reload in dev), Metaspace can grow unboundedly and eventually cause OutOfMemoryError: Metaspace. Always set -XX:MaxMetaspaceSize in production as a safety net.

Q1What are Functional Interfaces? Why were they added in Java 8? Is @FunctionalInterface mandatory?▾
🍳 Analogy

Before Java 8, to pass behaviour (a function) to another method, you had to write a full anonymous class — like hiring a full-time employee just to do one specific task once. Java 8's lambdas let you pass behaviour inline — like calling a freelancer for one job. A Functional Interface is the "job description" that says exactly one task is required.

A Functional Interface is simply an interface with exactly one abstract method. That one rule is all that matters. It can have any number of default or static methods — those don't count.

They were added to enable lambda expressions. Lambdas are anonymous functions. But Java is object-oriented — everything must be an object. So a lambda is secretly an instance of a functional interface. The single abstract method is what the lambda implements.

// Before Java 8 — verbose anonymous class just to pass behaviour
Runnable r = new Runnable() {
    public void run() {
        System.out.println("Hello");
    }
};

// Java 8 with lambda — same thing, 1 line
Runnable r = () -> System.out.println("Hello");

// Your own functional interface
@FunctionalInterface
interface Adder {
    int add(int a, int b);   // only ONE abstract method
    // default and static methods can exist freely
    default String describe() { return "I add numbers"; }
}

Adder sum = (a, b) -> a + b;
System.out.println(sum.add(3, 5)); // 8

// FizzBuzz using functional interface
@FunctionalInterface
interface FizzBuzzCheck {
    String check(int n);
}
FizzBuzzCheck fb = n ->
    n % 15 == 0 ? "FizzBuzz" :
    n % 3  == 0 ? "Fizz" :
    n % 5  == 0 ? "Buzz" :
    String.valueOf(n);
System.out.println(fb.check(15)); // FizzBuzz

Is @FunctionalInterface mandatory? No. Any interface with exactly one abstract method qualifies as a functional interface and can be used with lambdas — whether or not it has the annotation. But adding @FunctionalInterface is strongly recommended because: 1) it makes your intent clear to other developers 2) the compiler will give you a compile-time error if you accidentally add a second abstract method.

Q3Intermediate vs Terminal Stream operations — identify them in real code▾

Streams work in two phases. Intermediate operations are lazy — they don't execute immediately when called. They build up a pipeline. Terminal operations trigger the entire pipeline to run and produce a result or side effect.

Intermediate (Lazy)

  • filter() — keep elements matching predicate
  • map() — transform each element
  • flatMap() — flatten nested collections
  • sorted() — sort elements
  • distinct() — remove duplicates
  • limit(n) — take first n elements
  • skip(n) — skip first n elements
  • peek() — debug/side effect without changing pipeline

Terminal (Eager, triggers execution)

  • collect() — gather into collection
  • forEach() — consume each element
  • count() — count elements
  • reduce() — fold to single value
  • findFirst() / findAny()
  • anyMatch() / allMatch() / noneMatch()
  • min() / max()
  • toArray()
// Real example: process a list of employees
List<Employee> employees = getEmployees();

List<String> seniorDevNames = employees.stream()
    .filter(e -> e.getRole().equals("Developer"))  // intermediate
    .filter(e -> e.getExperience() > 5)             // intermediate
    .sorted(Comparator.comparing(Employee::getName)) // intermediate
    .map(Employee::getName)                          // intermediate
    .collect(Collectors.toList());                   // TERMINAL — runs everything

// Nothing above executed until collect() was called!

// Grouping with collectors
Map<String, List<Employee>> byDept = employees.stream()
    .collect(Collectors.groupingBy(Employee::getDepartment));

// Average salary per department
Map<String, Double> avgSalary = employees.stream()
    .collect(Collectors.groupingBy(
        Employee::getDepartment,
        Collectors.averagingDouble(Employee::getSalary)
    ));
⚠️ Common Parallel Stream Pitfalls

parallelStream() uses the common ForkJoinPool shared by the whole JVM. In a web server that already uses threads for requests, this can steal threads from request processing. It also has overhead for splitting and merging — for small lists it's actually slower than sequential. Never use it with mutable shared state without synchronization. Only use it for CPU-bound tasks on large data (10,000+ elements) in batch processing, never in web request handlers.

Q4CompletableFuture — async programming, key methods, chaining▾
🍳 Analogy

Old way: You go to a restaurant, order food, and STAND at the counter staring at the chef until your food is ready — blocking everything else. CompletableFuture: You order food, get a buzzer, go back to your table and do other things. When the buzzer goes off (future completes), you go pick it up. You can even say "when my food is ready, automatically bring it to my table" (thenAccept).

Without async programming, if your service calls a slow database or external API, the calling thread just sits and waits, doing nothing useful. CompletableFuture lets that thread be freed to handle other requests while the slow operation runs in the background.

// Basic async execution
CompletableFuture<String> future = 
    CompletableFuture.supplyAsync(() -> {
        // runs in ForkJoinPool thread, NOT the calling thread
        return callSlowExternalAPI(); 
    });

// Chain operations — each runs when previous completes
CompletableFuture<Void> pipeline = CompletableFuture
    .supplyAsync(() -> fetchUserFromDB(userId))          // async fetch
    .thenApply(user -> enrichWithProfile(user))          // transform result
    .thenApply(user -> user.toResponseDTO())             // transform again
    .thenAccept(dto -> sendToClient(dto))                // consume result
    .exceptionally(ex -> {                               // handle errors
        log.error("Failed: ", ex);
        return null;
    });

// Run two async tasks in PARALLEL and combine results
CompletableFuture<User>    userFuture    = CompletableFuture.supplyAsync(() -> fetchUser(id));
CompletableFuture<Orders>  ordersFuture  = CompletableFuture.supplyAsync(() -> fetchOrders(id));

// thenCombine: wait for BOTH, then combine
CompletableFuture<UserProfile> profile = userFuture
    .thenCombine(ordersFuture, (user, orders) -> 
        new UserProfile(user, orders));

// allOf: wait for ALL to complete
CompletableFuture.allOf(userFuture, ordersFuture).join();

// Use custom thread pool (important in web apps — don't use common pool)
ExecutorService pool = Executors.newFixedThreadPool(10);
CompletableFuture.supplyAsync(() -> slowTask(), pool);

Q1Internal working of ArrayList — when is a new array created? How does resizing work?▾
🍳 Analogy

Imagine a parking lot that starts with 10 parking spots. When all 10 are full and a new car arrives, the owner builds a new lot with 15 spots (50% bigger), drives all 10 cars from the old lot to the new one, parks the 11th car, and tears down the old lot. The driver didn't notice anything — the lot just got bigger.

ArrayList internally wraps a plain Object[] array. This is why it gives O(1) random access by index — it's literally array indexing. The default initial capacity is 10.

// Inside ArrayList source code (simplified)
public class ArrayList<E> {
    private Object[] elementData; // the backing array
    private int size;              // how many elements currently stored
    
    public ArrayList() {
        elementData = new Object[10]; // default capacity = 10
    }
    
    public boolean add(E element) {
        if (size == elementData.length) {
            // Array is full — grow by 50%
            int newCap = elementData.length + (elementData.length >> 1); // * 1.5
            elementData = Arrays.copyOf(elementData, newCap); // new array + copy
        }
        elementData[size++] = element;
        return true;
    }
}

The key performance implication: if you know you'll add 1000 elements, pre-size the list with new ArrayList<>(1000) to avoid 3-4 resize-and-copy cycles. Each copy is O(n), so multiple resizes on large lists wastes time.

Q2HashMap internal working — hashing, buckets, collisions, Red-Black tree. What happens when you put a duplicate key?▾
🍳 Analogy

A HashMap is like a large filing cabinet. Each drawer is a "bucket" (array index). When you file something, you first read the label (call hashCode), convert it to a drawer number (hash & capacity-1), open that drawer. If the drawer is empty, put it in. If the drawer already has something, check if it's the same label (equals). If yes — it's a duplicate key, replace the value. If different labels but same drawer — it's a collision, so you start a list of files in that drawer. In Java 8+, once a drawer has 8+ files, the list upgrades to a faster Red-Black tree for O(log n) search.

// Step-by-step: what happens when you call map.put("name", "Alice")

// Step 1: compute hash
int hash = key.hashCode();           // "name".hashCode() = some number
hash = hash ^ (hash >>> 16);       // secondary hash to spread better

// Step 2: find bucket index
int index = hash & (capacity - 1);  // if capacity=16, index is 0-15

// Step 3: check bucket
// If empty → create new Node and place there
// If occupied → traverse the linked list/tree
//   → if key.equals(existingKey) → UPDATE the value (duplicate key!)
//   → if key doesn't equal → add new Node to the chain (collision)

// Step 4: check if resize needed
// if (size > capacity * loadFactor) → double capacity, rehash everything
// Default: 16 * 0.75 = 12 entries before resize to 32

When a duplicate key is put: The existing entry's value is overwritten with the new value. The key count does not increase. put() returns the old value that was replaced.

Collision resolution evolution:

  • Bucket has 0-7 entries → stored as a singly-linked list (Node)
  • Bucket reaches 8 entries AND total capacity ≥ 64 → upgraded to a Red-Black Tree (TreeNode) → O(log n) lookup instead of O(n)
  • If the tree shrinks back to 6 entries → converts back to linked list
📋 Why override BOTH hashCode() and equals()?

hashCode() determines WHICH bucket the key goes to. equals() determines WHICH entry within that bucket is the same key. If two objects are "equal" by your business logic but have different hashCodes, they'll land in different buckets and HashMap will treat them as different keys — completely broken. Always override both together.

// CORRECT custom key in HashMap
class Employee {
    int id; String name;
    
    @Override
    public int hashCode() {
        return Objects.hash(id, name); // same fields as equals
    }
    @Override
    public boolean equals(Object o) {
        if (!(o instanceof Employee)) return false;
        Employee e = (Employee) o;
        return this.id == e.id && Objects.equals(this.name, e.name);
    }

Q3ConcurrentHashMap vs Hashtable vs Collections.synchronizedMap — which when?▾

Hashtable — every single method (get, put, remove, size, containsKey) is synchronized on the entire Hashtable object. This means only ONE thread can do ANYTHING to it at a time. If Thread A is doing a get() on key "user123", Thread B cannot even do a get() on key "order456" even though they're completely separate entries. This is terrible performance.

Collections.synchronizedMap() wraps any map with synchronized blocks. Similar to Hashtable — one lock for the whole map. Fine for simple use cases but iteration still needs external synchronization.

ConcurrentHashMap (Java 8) uses a completely different approach:

  • For reads (get) — no lock at all. Uses volatile reads. Multiple threads can read simultaneously.
  • For writes (put) — locks only the specific bucket being modified using CAS (Compare-And-Swap) or a synchronized block on just that bucket's Node. Two threads writing to completely different buckets proceed in parallel.
  • Result: near-HashMap performance with full thread safety.
// DO NOT USE in multithreaded code
Hashtable<String,String> ht = new Hashtable<>(); // one lock, slow

// BETTER — but still one lock for whole map
Map<String,String> sm = Collections.synchronizedMap(new HashMap<>());

// BEST for concurrent access
ConcurrentHashMap<String,String> chm = new ConcurrentHashMap<>();
chm.put("k1", "v1");

// Atomic operations that are NOT possible with regular HashMap
chm.putIfAbsent("k1", "newValue");  // only put if key not present, atomically
chm.computeIfAbsent("k2", k -> loadFromDB(k)); // compute value if absent
chm.merge("counter", 1, Integer::sum);  // atomic increment pattern
📋 ConcurrentHashMap does NOT allow null keys or null values

HashMap allows one null key and null values. ConcurrentHashMap doesn't — because null creates ambiguity: if get("key") returns null, you can't tell if the key doesn't exist or if the value is null. In concurrent code, this ambiguity causes bugs.

Q4Comparator vs Comparable — implement Employee sorting by descending salary▾

Comparable — the class defines its own natural ordering. Think of it as "I know how to compare myself to others of my type." Implement compareTo() in the class itself. Example: String, Integer, LocalDate all implement Comparable — that's why they sort naturally.

Comparator — an external comparison strategy. Think of it as "a judge who compares two things by some criteria." You don't need to modify the class. You can have multiple Comparators for the same class (sort by salary, sort by name, sort by age — all different Comparators).

Q5How to create an Immutable class? Why are they needed? Deep cloning?▾

An immutable class is one whose state cannot change after the object is created. String is the most famous example. Benefits: automatically thread-safe (no synchronization needed), safe as HashMap keys (hashCode won't change), simpler reasoning about program state.

📋 Recipe for an Immutable Class
  • Mark the class final — prevents subclasses from adding mutability
  • Make all fields private final
  • No setters anywhere
  • Initialize all fields in the constructor only
  • For mutable fields (List, Date, arrays): accept a deep copy in the constructor, return a deep copy in getters — never the original reference
public final class ImmutableEmployee {
    private final int id;
    private final String name;
    private final List<String> skills;  // mutable — needs defensive copy!
    private final Date joiningDate;     // mutable — needs defensive copy!
    
    public ImmutableEmployee(int id, String name, 
                              List<String> skills, Date joiningDate) {
        this.id = id;
        this.name = name;

        this.skills = List.copyOf(skills); // Java 10+, or new ArrayList<>(skills)
        // Defensive copy of mutable Date
        this.joiningDate = new Date(joiningDate.getTime());

    public List<String> getSkills() {
        return Collections.unmodifiableList(skills); // or new copy
    }
    
    public Date getJoiningDate() {
        return new Date(joiningDate.getTime()); // defensive copy on get too
    }
    // No setters! Only getters.
}

🍳 Analogy

Checked exception: You're going on a road trip. Your GPS warns you "Road closed ahead — plan a detour before you leave." The compiler (GPS) forces you to handle it before the program runs. Unchecked exception: You're driving and suddenly get a flat tire — unexpected, no advance warning, happens at runtime. You can choose to handle it or let it propagate.

Checked Exceptions — Extend Exception (not RuntimeException). The compiler forces you to either catch them with try-catch or declare them with throws. }

Q2Output of finally block with return? When does finally NOT execute?▾

The output of the code in the question is:

In try block
In finally block
Result: 30

Why 30? The finally block always executes before the method actually returns. When both try and finally have return statements, the finally's return wins and completely replaces the try's return value. The return 10 in try was about to return, but finally intercepted it, executed, and returned 30 instead. This is why you should NEVER put a return statement inside a finally block — it can also silently swallow exceptions:

try {
    throw new RuntimeException("something failed");
} finally {
    return 42; // SWALLOWS the exception! Caller never knows it failed!
}

The finally block does NOT execute in these scenarios:

  • System.exit() is called — JVM terminates immediately
  • JVM crashes or is killed with kill -9
  • The thread running the try block is forcibly stopped
  • The try block contains an infinite loop with no exit condition
✅ Best Practice

Use finally only for cleanup (close resources, release locks). For resource cleanup specifically, prefer try-with-resources instead — it's cleaner and handles exceptions properly.

Q3Try-with-resources — how it works, Java 9 change, when to use?▾

Try-with-resources (Java 7) automatically calls close() on any resource that implements AutoCloseable when the try block exits — whether normally or due to an exception. No more forgetting to close in finally.

// OLD WAY — easy to forget close, messy error handling
Connection conn = null;
PreparedStatement stmt = null;
try {
    conn = dataSource.getConnection();
    stmt = conn.prepareStatement("SELECT ...");
    // use stmt
} catch (SQLException e) {
    e.printStackTrace();
} finally {
    try { if (stmt != null) stmt.close(); } catch (SQLException e) {}
    try { if (conn != null) conn.close(); } catch (SQLException e) {}
}

// JAVA 7 try-with-resources — auto-closes in REVERSE declaration order
try (Connection conn = dataSource.getConnection();
     PreparedStatement stmt = conn.prepareStatement("SELECT ...")) {
    // use stmt and conn
} catch (SQLException e) {
    e.printStackTrace();
}
// stmt.close() called first, then conn.close() — automatically!

// JAVA 9 improvement — use existing effectively-final variable
Connection conn = dataSource.getConnection();
try (conn) {   // Java 9+: just reference the variable
    // use conn
}

Try-with-resources also handles the tricky case where both the try body AND the close() method throw exceptions. The close() exception is "suppressed" (attached to the main exception) instead of replacing it, so you don't lose the original error.

Q4Exception propagation + overriding method and additional exceptions rule▾

Exception Propagation — When an exception is thrown and not caught in a method, it propagates to the caller, then to the caller's caller, all the way up the call stack. If nobody catches it and it reaches main(), the program prints the stack trace and terminates.

void methodC() { throw new RuntimeException("oops"); }  // thrown here
void methodB() { methodC(); }    // not caught — propagates UP to methodA
void methodA() {
    try {
        methodB();
    } catch (RuntimeException e) {
        System.out.println("Caught here: " + e.getMessage()); // caught!
    }
}

Rules for overriding methods and exceptions:

📋 The Overriding Exception Rules
  • Child can throw fewer checked exceptions than parent — ✅ fine
  • Child can throw narrower checked exceptions (subclass) — ✅ fine
  • Child can throw new or broader checked exceptions — ❌ compile error
  • Child can throw any unchecked (RuntimeException) — ✅ always allowed
class Parent {
    void method() throws IOException { }
}

class Child extends Parent {
    void method() throws FileNotFoundException { }  // ✅ narrower
    // void method() throws Exception { }            ❌ broader — won't compile

    // void method() throws RuntimeException { }     ✅ unchecked, always OK

Q1Why is String immutable? How many objects are created — new String("Shiv") vs "Shiv" vs "Shiv"?▾

String's internal character data is stored in a private final byte[] array (since Java 9). No method in String class ever modifies this array — every operation that seems to modify a String (like toUpperCase, concat, replace) actually creates and returns a new String object.

Why immutable?

  • String Pool / caching — Since strings can't change, the JVM can safely have multiple references point to the same String object in the pool. If strings were mutable, one reference changing "hello" to "HELLO" would affect everyone pointing to it.
  • Security — Strings are used for class names, file paths, database passwords, hostnames. If they were mutable, malicious code could change these after a security check passes.
  • Thread safety — Immutable objects are automatically thread-safe. No synchronization needed when sharing strings between threads.
  • HashCode caching — String caches its hashCode the first time it's calculated. Since the value can't change, this is safe and makes HashMap lookups fast.

Object count questions — how many objects are created?

Q2synchronized keyword — method vs block, instance vs static, internal working (monitorenter/exit)▾

Every Java object has a built-in lock called a monitor (or intrinsic lock). synchronized tells the JVM: acquire this monitor before entering, release it when exiting. Only one thread can hold a monitor at a time.

// Synchronized instance method — lock is 'this' (the object instance)
class Counter {
    private int count = 0;
    
    public synchronized void increment() {  // lock = this Counter object
        count++;
    }
    
    public synchronized void decrement() {  // SAME lock as increment()
        count--;                               // If thread holds lock in increment,
    }                                          // no thread can enter decrement either!
}

// Synchronized STATIC method — lock is Counter.class (the Class object)
public synchronized static void staticMethod() {
    // lock = Counter.class — shared across ALL instances
}

// Synchronized block — you choose the lock object, minimize critical section
private final Object lock1 = new Object();
private final Object lock2 = new Object();

public void updateBalance() {
    doSomeNonCriticalWork();    // no lock needed here
    synchronized(lock1) {      // only lock what needs protection
        balance += amount;
    }
    doMoreNonCriticalWork();    // no lock needed here
}

Internally — the JVM inserts monitorenter bytecode at the start of a synchronized block and monitorexit at every exit point (normal exit AND exception). Modern JVMs optimize aggressively: if only one thread ever accesses an object, they use biased locking (no actual lock operation). Under moderate contention, lightweight/spin locking with CAS. Only under heavy contention do they fall back to OS-level mutex (heaviest).

📋 Key Trap: Two threads, two synchronized methods on SAME object

If Thread A is inside synchronized method increment(), Thread B CANNOT enter synchronized method decrement() on the same object — even though they're different methods. Both use the same lock (this). They would block each other.

Q3wait(), notify(), notifyAll() — why in Object class? wait() vs sleep()?▾

These methods are in the Object class, not in Thread. Why? Because they operate on the object's monitor lock, not on threads. In Java, any object can be used as a lock. So the ability to wait and notify must belong to every object, not just to Thread objects.

// Classic producer-consumer with wait/notify
class SharedBuffer {
    private Queue<Integer> buffer = new LinkedList<>();
    private final int MAX_SIZE = 5;
    
    public synchronized void produce(int item) throws InterruptedException {
        while (buffer.size() == MAX_SIZE) {
            wait(); // buffer full — release lock, wait for consumer
        }          // use while not if — guard against spurious wakeups
        buffer.add(item);
        notifyAll(); // wake up consumers waiting for items
    }
    
    public synchronized int consume() throws InterruptedException {
        while (buffer.isEmpty()) {
            wait(); // buffer empty — release lock, wait for producer
        }
        int item = buffer.poll();
        notifyAll(); // wake up producers waiting for space
        return item;
    }
}

Thread pool sizing rules of thumb:

  • CPU-bound tasks (heavy computation): pool size = number of CPU cores. More threads than cores means context switching overhead with no benefit.
  • I/O-bound tasks (DB calls, HTTP requests, file operations): Threads spend most time waiting. Formula: pool size = cores × (1 + wait_time / compute_time). If a DB call takes 100ms and processing takes 10ms, ratio = 11, so 8 cores → 88 threads.
⚠️ Executors.newFixedThreadPool uses UNBOUNDED queue

Under heavy load, tasks pile up in the queue. With 10,000 waiting tasks each holding request data, you'll get OutOfMemoryError. Always use ThreadPoolExecutor with a bounded ArrayBlockingQueue and an appropriate rejection policy in production.

Runnable vs Callable: Runnable's run() returns void and cannot throw checked exceptions. Callable's call() returns a value (wrapped in Future) and CAN throw checked exceptions. Use Callable when you need the result or need to propagate checked exceptions.

Q5Spring caching — @Cacheable, @CachePut, @CacheEvict. How does it work internally?▾

Spring caching uses AOP (Aspect-Oriented Programming) proxies. When you call a @Cacheable method, you're actually calling a proxy that wraps your method. The proxy checks the cache first using CacheManager → Cache → key lookup. If there's a cache hit, it returns the cached value and your method never executes. If miss, it calls your real method, stores the result, and returns it.

@Service
public class UserService {
    
    // Check cache first. Call method only on cache miss. Cache the result.
    @Cacheable(value = "users", key = "#id")
    public User findUser(Long id) {
        return userRepository.findById(id).orElseThrow();
    }
    
    // Always call method AND update cache. Use after update operations.
    @CachePut(value = "users", key = "#user.id")
    public User updateUser(User user) {
        return userRepository.save(user); // fresh result goes back to cache
    }
    
    // Remove from cache. Use after delete operations.
    @CacheEvict(value = "users", key = "#id")
    public void deleteUser(Long id) {
        userRepository.deleteById(id);
    }
    
    // Conditional caching — only cache if result is not null
    @Cacheable(value = "users", key = "#email", 
               condition = "#email != null", 
               unless = "#result == null")  // unless: don't cache if result is null
    public User findByEmail(String email) { ... }
}

@SpringBootApplication

public class Application { ... }

Q2EAGER vs LAZY loading, N+1 query problem — how does it happen, how to solve?▾

EAGER loading — Related entities are loaded immediately along with the parent. @ManyToOne and @OneToOne default to EAGER.

LAZY loading — Related entities are loaded only when you first access them (via a Hibernate proxy). @OneToMany and @ManyToMany default to LAZY. More efficient for large collections you might not always need.

N+1 Problem — The most common Hibernate performance killer. Classic scenario: You fetch 100 Orders. Each Order has a Customer relationship. When your code accesses each order's customer, Hibernate fires a separate SQL per order. That's 1 (for orders) + 100 (for customers) = 101 queries for what could be done in 1 JOIN.

// ❌ N+1 happening — this looks innocent but fires 101 SQL queries
List<Order> orders = orderRepo.findAll();    // 1 query
for (Order o : orders) {
    System.out.println(o.getCustomer().getName()); // 1 query PER order!
}

// ✅ Fix 1: JOIN FETCH — one query with a JOIN
@Query("SELECT o FROM Order o JOIN FETCH o.customer WHERE o.status = :status")
List<Order> findWithCustomers(@Param("status") String status);
// Generates: SELECT o.*, c.* FROM orders o INNER JOIN customer c ON ...

// ✅ Fix 2: @EntityGraph — declarative, no JPQL
@EntityGraph(attributePaths = {"customer", "items"})
List<Order> findAll();

// ✅ Fix 3: @BatchSize — fetch in batches instead of one-by-one
@OneToMany(mappedBy = "order")
@BatchSize(size = 50) // fetches 50 at once instead of 1 at a time
private List<OrderItem> items;
⚠️ How to detect N+1 in development

Add spring.jpa.show-sql=true and logging.level.org.hibernate.SQL=DEBUG to application.properties. You'll see every SQL query in the logs. If you see the same query repeating with different IDs — you have N+1. In production, use Hibernate Statistics or a tool like Datasource-Proxy to count queries per request.

Q1ACID properties — explain each with real example▾
🍳 Analogy — Bank Transfer

You transfer ₹1000 from Account A to Account B. ACID ensures this doesn't go wrong in any scenario.

  • Atomicity — "All or nothing." Deducting ₹1000 from A and adding ₹1000 to B happen as one unit. If the server crashes between the two operations, the whole transaction rolls back — no money disappears or appears from nowhere.
  • Consistency — Data goes from one valid state to another valid state. If A has ₹500 and you try to deduct ₹1000, the transaction is rejected (violates constraint). The database remains consistent.
  • Isolation — Concurrent transactions don't interfere. If two people transfer from A simultaneously, they don't see each other's partial updates. Isolation levels (Read Uncommitted → Read Committed → Repeatable Read → Serializable) control how much concurrent transactions affect each other.
  • Durability — Once a transaction commits, it persists even if the server crashes immediately after. The DB writes to disk/WAL (Write-Ahead Log) before acknowledging commit.
Q2SQL execution order. WHERE vs HAVING. Complex queries — 2nd salary, top 3 per dept.▾

SQL clauses are written in one order but executed in a different order. This explains why you can't use a SELECT alias in WHERE.

-- Execution order (NOT the writing order)
-- 1. FROM — identify the tables
-- 2. JOIN — combine tables
-- 3. WHERE — filter rows (BEFORE grouping)
-- 4. GROUP BY — group remaining rows
-- 5. HAVING — filter groups (AFTER grouping, can use aggregates)
-- 6. SELECT — choose columns (aliases created here)
-- 7. ORDER BY — sort results
-- 8. LIMIT/OFFSET — paginate

-- WHERE vs HAVING — the key difference
SELECT dept, COUNT(*), AVG(salary)
FROM employee
WHERE salary > 30000          -- filter rows BEFORE group (no aggregates)
GROUP BY dept
HAVING COUNT(*) > 5           -- filter groups AFTER (can use COUNT)
ORDER BY AVG(salary) DESC;
-- 2nd highest salary (without window functions)
SELECT MAX(salary) AS second_highest
FROM employee
WHERE salary < (SELECT MAX(salary) FROM employee);

-- Nth highest salary using window function (better, handles ties)
SELECT name, salary
FROM (
    SELECT name, salary,
           DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
    FROM employee
) ranked
WHERE rnk = 2;

-- Top 3 highest paid per department
SELECT dept, name, salary
FROM (
    SELECT dept, name, salary,
           ROW_NUMBER() OVER (
               PARTITION BY dept       -- reset ranking per department
               ORDER BY salary DESC    -- highest salary = rank 1
           ) AS row_num
    FROM employee
) ranked
WHERE row_num <= 3
ORDER BY dept, salary DESC;

-- Employees earning more than avg salary of their own department
SELECT e.name, e.salary, e.dept
FROM employee e
WHERE e.salary > (
    SELECT AVG(salary) 
    FROM employee e2 
    WHERE e2.dept = e.dept     -- correlated subquery: re-runs for each row
);

-- Better version using window function (single scan)
SELECT name, salary, dept
FROM (
    SELECT name, salary, dept,
           AVG(salary) OVER (PARTITION BY dept) AS dept_avg
    FROM employee
) t
WHERE salary > dept_avg;

Q2Saga Pattern — Choreography vs Orchestration, compensating transactions, failure handling▾

In microservices, you can't use a traditional database transaction across multiple services — each service has its own database. The Saga pattern solves distributed transactions by breaking them into a sequence of local transactions, each with a compensating transaction for rollback.

Choreography-based Saga

  • No central coordinator
  • Each service publishes an event when its step completes
  • Next service listens for that event and does its step
  • If something fails, a failure event triggers compensation backwards
  • Good: decoupled, no single point of failure
  • Bad: hard to track overall flow, debugging is complex

Orchestration-based Saga

  • Central Saga Orchestrator tells each service what to do next
  • Orchestrator tracks state and decides next step based on responses
  • Good: easy to visualize and monitor the flow
  • Bad: orchestrator can become a bottleneck or single point of failure
// Example: Place Order Saga (Orchestration)
// Steps: 1. Reserve Inventory → 2. Process Payment → 3. Schedule Delivery
// If Payment fails:
// Compensating transaction: Release Inventory (undo step 1)
// If Delivery fails:
// Compensating: Refund Payment, Release Inventory (undo steps 2 and 1)

class OrderSaga {
    void execute(Order order) {
        try {
            inventoryService.reserve(order);        // Step 1
            paymentService.charge(order);           // Step 2
            deliveryService.schedule(order);        // Step 3
        } catch (PaymentException e) {
            inventoryService.release(order);        // Compensate step 1
        } catch (DeliveryException e) {
            paymentService.refund(order);           // Compensate step 2
            inventoryService.release(order);        // Compensate step 1
        }
    }
}

Idempotency in Saga steps is crucial — if a step is retried (network timeout, crash), it must be safe to execute multiple times. Use idempotency keys (unique operation ID) to detect and skip already-processed requests.

Q3Circuit Breaker — states, implementation with Resilience4j, retry with exponential backoff▾
🍳 Analogy

Exactly like an electrical circuit breaker. When current (failures) is too high, the breaker trips (OPEN) to protect the circuit. After a cool-down period, it half-opens to test if things are normal. If yes, it resets to CLOSED. This prevents a failing downstream service from causing a cascade failure in your service.

// application.yml — Resilience4j circuit breaker config
resilience4j:
  circuitbreaker:
    instances:
      paymentService:
        failureRateThreshold: 50        # open if 50% of calls fail
        waitDurationInOpenState: 10000  # wait 10s before trying half-open
        slidingWindowSize: 10           # evaluate last 10 calls
        permittedNumberOfCallsInHalfOpenState: 3
  retry:
    instances:
      paymentService:
        maxAttempts: 3
        waitDuration: 1000             # 1s between retries
        enableExponentialBackoff: true  # 1s, 2s, 4s... 
        exponentialBackoffMultiplier: 2
// Usage in service
@CircuitBreaker(name = "paymentService", fallbackMethod = "paymentFallback")
@Retry(name = "paymentService")
@TimeLimiter(name = "paymentService")  // timeout
public CompletableFuture<PaymentResult> processPayment(PaymentRequest req) {
    return CompletableFuture.supplyAsync(() -> paymentClient.pay(req));
}

public CompletableFuture<PaymentResult> paymentFallback(PaymentRequest req, Exception ex) {
    log.warn("Payment service unavailable, using fallback", ex);
    return CompletableFuture.completedFuture(PaymentResult.pending(req.getId()));
}

Circuit Breaker states:

  • CLOSED — Normal operation. All requests pass through. Failure rate is tracked.
  • OPEN — Failure rate exceeded threshold. ALL requests immediately get the fallback response without calling the downstream service. This gives the downstream time to recover.
  • HALF-OPEN — After the wait duration, a few test requests are allowed. If they succeed → back to CLOSED. If they fail → back to OPEN.
Q4CAP Theorem — what is it? Which do you choose? 12-Factor App?▾

CAP Theorem states that a distributed system can only guarantee 2 of these 3 properties simultaneously:

C — Consistency

Every read gets the most recent write or an error. All nodes see the same data at the same time.

A — Availability

Every request gets a response (not guaranteed to be the latest data). System never rejects requests.

P — Partition Tolerance

System continues operating despite network partitions (nodes can't communicate).

Since network partitions are a reality in distributed systems, P is always required. So your real choice is between CP and AP:

ChoiceExamplesWhen to use
CP (Consistent + Partition-tolerant)ZooKeeper, HBase, MongoDBBanking, inventory — you'd rather fail than show wrong data
AP (Available + Partition-tolerant)Cassandra, Couchbase, DynamoDBSocial feed, product catalog — stale data ok, must stay available

Q5Service Discovery — what and why? Distributed Tracing — traceId/spanId propagation?▾

Service Discovery — In microservices running on Kubernetes or cloud, service instances start and stop constantly (scaling, crashes, deployments). Their IP addresses change. You can't hardcode IPs. Service discovery lets services find each other by name.

  • Client-side discovery (Eureka) — Services register with a service registry on startup. When ServiceA wants to call ServiceB, it asks the registry for ServiceB's current instances and does the load balancing itself (using Ribbon/Spring Cloud LoadBalancer).
  • Server-side discovery (Kubernetes) — The platform handles routing. ServiceA calls "http://payment-service/pay" and Kubernetes DNS resolves it and routes to a healthy pod. No client-side library needed.

Distributed Tracing — When a user request touches 8 microservices, if something fails or is slow, which service is responsible? Distributed tracing assigns a traceId at the entry point (API Gateway) and propagates it through every service call. Each service creates a spanId for its own processing. Tools like Zipkin or Jaeger collect all spans and show you the full request timeline visually.
